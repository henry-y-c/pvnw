# PVNW — Progressive Vibe Notes Writing

1. **定位**：PVNW 是原任务的判断层，不是要求把每次对话写成笔记的任务生成器。
2. **宿主边界**：目标是由宿主在每项可见任务开始、原任务搜索／执行前调用本 Skill；客户端须自行发现并配置该入口。仅改此文件不能使任一客户端自动加载、跨会话记住退出、获得写权限或保证实际效果。

## Workflow：任务前准入 → 获权建档 → 边做边记 → 交付（不自动写）

> 顺序是条件性的：**每项任务判断，不是每项任务建 Vault**。需留痕时，把只读定位、目录确认和写权关口放在主体搜索／研究／执行之前；缺授权先问，不能先做完再问放哪里。文件系统可写不等于有权写；无适用 Vault 且获准唯一新位置时才创建兼容文件夹。宿主未调用本 Skill 时，此流程不会自行运行。

1. **先辨认出口与思考强度**：用户原本要解决什么、怎样算回答了？能可靠直接回答、没有后续价值的简单问题只答、不为建档索权；需查证、比较、分解、取舍或多步执行的问题优先视为值得留痕，不以“用户没说记笔记”否决。宿主调用后、原任务搜索／执行前做轻量判断；获权的研究任务先建安全入口再开始执行，同时不能以建档代替回答。细则见 [decision-gates](references/decision-gates.md)。
2. **尊重退出**：用户明确“不启动／不记录”时，按指定范围退出；未指明范围仅限当前独立任务，不为退出单独造记录，也不为建 Vault 打断原题。跨会话、长期退出若无可验证的宿主记忆，不能承诺持续有效。
3. **先核已有专题，再判是否新建**：对于需留痕的任务，在主体工作前先只读核当前工作空间规则、已选目录及已有获权 Vault／专题，再逐项确定目标位置、建目录／新文件及必要各层修改的授权；优先续记适用的既有工作包。本轮新观察、纠偏或人的取舍即使不改变里程碑结论，只要影响后续判断就按获权范围及时续记。需要思考的独立研究若值得回查，则考虑新专题而非先做完研究再决定；缺唯一位置或所需写权时，**先向有权者问一个必要的位置与许可问题，待确认后再做主体工作**，不等答案写完才问。若拒绝／无法获得许可，不创建，仍尽可能安全回答原题并说明未持久化；纯复述或无后续价值只回答。价值不等于许可。
4. **托管建系与 Vault**：按 [routes-and-lifecycle](references/routes-and-lifecycle.md) 选择既有专题或新专题；优先使用**有权者选定的唯一授权位置**，已有获权 Vault 就在其获权范围内复用，已选普通 Markdown 目录也保留。只有本次有权者明确授权，或当前工作空间可见的托管策略明确授权建目录、根／目标／包文件，并指定无 Vault 时的唯一位置，且没有适用的既有目标，才在该位置创建 Obsidian 兼容的 `.md` 文件夹／相对链接；Obsidian 程序是否安装无关，不默认创建 `.obsidian`。已有获权 Vault 不另造，已选普通 Markdown 目录不被别处 Vault 覆盖；无位置或冲突先确认。获权的真实研究先建有内容的根导航→目标现状→已启动工作包过程入口，再执行、逐步记录；缺权限或真实问题／规划依据就报告不完整，不造空篇。旧库重构先只读盘点、旧→新映射和可验证恢复点，获准后分批验证及回滚；创建、各层修改、移动／删除、Git、公开与安装各自核权。项目的命名／WBS／生命周期见 [project-system](references/project-system.md)。
5. **安全与持续授权**：每次实际写入前检查内容、文件名、相对链接和 Git 扩散风险。持续维护或托管建系权须有当前明确指令或可核实的适用工作空间／项目规则，限定目标位置、专题范围、允许创建／修改的层级与动作；一次建系同意不自动延续为跨任务写权，也不授权新文件、搬删、Git 或安装。托管策略可明确授予限范围的后续建档与启动目标权限，但不推定其它权限；无权时说明拟续记范围并请人确认，本任务禁止记录优先。仅有唯一获授权、安全可写目标且归属暂未定时，才**考虑**目标内最小安全收件线索；不是自动授权。见 [safe-inbox](references/safe-inbox.md) 与 [provenance-and-permissions](references/provenance-and-permissions.md)。
6. **项目管理三层与统一写法**：获权新建时宏观 macro 根 `0_<name>.md` 管项目导航；中观 meso 里程碑 `N_<dir name>/N.0_<name>.md` 管目标／节点／工作包入口；同目录 `N.1_<name>.md`、`N.2_<name>.md`… 各为一个微观 micro WBS 工作包，**篇内按真实先后记录该包整个执行过程**。先判断是否续题／新专题，提出一个或几个独立可验收目标及证据门槛；由有权者确认启动或由可见托管策略在限定范围内委托启动，才分配稳定号；只展开当前目标中确需跟踪的 WBS，按交付而非搜索次数拆包。研究前有真实问题、计划、未执行状态和创建权就建当前包篇；执行中每个安全、可观察的步骤完成后及时追加动作／结果／失败，未做的不写成已做。旧 `N.W1`／`N-1` 不自动迁移。整个 Skill 的 Markdown 和获权新笔记都按**清单体笔记**组织：一维用四空格缩进的嵌套有序列表；多对象×稳定字段才用局部管道表格，同格多项就地以 `1. …<br>2. …` 视觉编号；不强套表格或空栏目。加粗标签用 `**标签**：正文`，交付前检查受影响 Markdown 的裸露星号；能访问目标阅读器则抽查显示，否则标渲染未验证，不把标点包进加粗后紧贴汉字。工作包完成不等于节点通过，AI 判断不等于人的冻结。采用 micro→摘要链时，每次工作包篇变更都在同一逻辑变更跟进摘要进展或入口；根仅在项目范围／全局风险或待决策、目标状态／关系或导航实变时更新。写前预检各层独立授权，逐级核根→目标→工作包／安全证据及反向入口。**不是每项任务强制创建三份文件**。见 [project-system](references/project-system.md) 与 [note-modeling](references/note-modeling.md)。
7. **每包 Git 检查点**：已启动 WBS 每做完一个可核验的交付包（或形成有证据的受阻出口），先完成该包过程、必要摘要及链接同步，再判断一次本地提交；WBS 状态／证据／依赖实变须同批跟进摘要，小修正并入本轮批次，同包多次观察不逐步／逐行提交；里程碑节点推进／复评另核获权上层入口。仅在已有 Git 仓库、项目规则或本次指令明确授权本地 commit、且没有当前禁令时，核拟提交快照、安全与既有暂存后限范围提交；无本地提交授权就请人确认，明确禁止 commit 才不提交；不自动 git init，仅禁止 push 不挡获权本地 commit，始终不自动 push。细则见 [provenance-and-permissions](references/provenance-and-permissions.md)。
8. **最后回到出口**：交付时回答原问题，明确做了什么、没做什么、哪些是人的决定、AI 推断、实际验证与未验证；若未落盘就直说，涉及 Git 再报告提交与剩余改动，不宣称跨宿主已经触发。用 [acceptance-cases](references/acceptance-cases.md) 核查纸面反例。

## 原则是推理，不是打勾

1. **实事求是**：区分材料、人的决定、AI 推断与本机实测；不足以回答原问题时说不确定，不把“字段齐全”当真相。
2. **解放思想**：对问题的隐含假设给出有依据的替代模型，并用反例检查；不把现成模板或宿主习惯当天然正确。
3. **知行合一**：提出能回应原问题的下一步、实际执行与观察结果；不能执行或验证时标清边界，而不是只报告流程通过。
